# Share-Link Multiplayer Design

## Goal

Add online two-player Quoridor matches where one player creates a room and shares a URL with another player. The first production-ready version should preserve the existing single-file game feel while adding a small Node.js server that hosts the page and synchronizes game state through WebSockets.

## Scope

Included:

- Create a match room and generate a shareable link.
- Join a match room from the shared link.
- Assign the first connected player to the bottom pawn and the second connected player to the top pawn.
- Keep both browsers synchronized after pawn moves, wall placements, restarts, disconnects, and reconnects.
- Preserve the existing bot mode as a playable option.
- Deploy as one Node.js web service that serves the static game and handles WebSocket traffic.

Excluded from the first version:

- User accounts, login, ranked matchmaking, spectator mode, chat, persistent match history, and anti-cheat beyond server-side turn validation.

## Hosting

The recommended hosting target is Render as a Node Web Service because it supports long-lived WebSocket connections and fits this app's simple "one server process" architecture. Railway is a reasonable alternate target. The app will expose one HTTP server:

- `GET /` serves the game page.
- `GET /?room=CODE` opens the game and attempts to join `CODE`.
- `WS /ws` handles room creation, joins, moves, wall placement, restart, presence, and state sync.

## Architecture

The current `index.html` keeps rendering, input handling, rules, pathfinding, bot behavior, and state in one script. The multiplayer change should extract the game rules into shared client/server logic so the browser can preview legal input while the server remains the source of truth for online matches.

Planned files:

- `index.html`: UI shell and browser client.
- `src/game.js`: pure Quoridor state, move validation, wall validation, win detection, and serialization.
- `src/bot.js`: existing bot decision logic for local bot mode.
- `server.js`: HTTP static server plus WebSocket room manager.
- `package.json`: Node scripts and dependencies.

## Data Flow

Bot mode remains local:

1. Browser creates local state.
2. Player acts.
3. Browser validates and applies the action.
4. Bot chooses and applies an action.
5. Browser renders.

Online mode is server-authoritative:

1. Browser sends `createRoom` or `joinRoom`.
2. Server assigns a side and sends the canonical room state.
3. Browser enables input only when it is that player's turn.
4. Browser sends an action request: `move`, `wall`, or `restart`.
5. Server validates against canonical state, applies legal actions, and broadcasts the new state.
6. Browser renders the broadcast state.

## Room Rules

- Room codes are short, uppercase, and generated by the server.
- A room has at most two active players.
- If a player disconnects, their side is marked disconnected but the room stays alive for a short in-memory grace period.
- If the same room link is opened again while a side is disconnected, the server may reassign the new connection to that side.
- Rooms are in-memory for the first version. Restarting the server clears active rooms.

## UI

Add a compact mode control near the existing side panel:

- `Vs Bot`
- `Online`

In online mode, replace the bot difficulty controls with connection controls:

- Create match button.
- Join status when `?room=CODE` is present.
- Copy link button after a room is created or joined.
- Player side labels: `You` and `Opponent`.
- Status text: waiting for opponent, your turn, opponent turn, disconnected, reconnecting, game over.

The board should continue to use the existing movement highlights and wall previews. In online mode, highlights show only for the local player's legal turn.

## Error Handling

- Illegal local clicks show the existing warning feedback.
- Server-rejected actions show a warning and then re-render the latest canonical state.
- Full room shows a clear "room is full" status.
- Unknown or expired room code shows a clear "room not found" status with a create-new option.
- WebSocket disconnect disables board input and shows reconnecting/disconnected status.

## Testing

Minimum verification:

- Unit tests for pure rules: pawn movement, jump movement, wall legality, path preservation, win detection, and serialization.
- Integration smoke test for WebSocket room creation, joining, move broadcast, wall broadcast, restart, and room-full rejection.
- Browser/manual test at desktop and mobile widths for bot mode and online mode.

## Deployment

Deployment steps:

1. Push the repository to `https://github.com/FilipBugarin/quoridor.git`.
2. Create a Render Web Service from that repository.
3. Set build command to `npm install`.
4. Set start command to `npm start`.
5. Use Render's public URL as the base for share links.

The first deployed share links will look like:

```text
https://<render-service-name>.onrender.com/?room=ABCD
```
